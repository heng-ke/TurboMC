## 二、三个必须一起解决的技术问题

### 1. 自定义积木的函数体目前**看不见**

`Sb3Importer` 现在这样处理：

```java
if (opcode.startsWith("procedures_definition")) {
    return convert(blocks, nextId(block), ...);   // 跳过定义块，只接后续
}
```

后果：定义块本身不显示，**函数体也不会挂到任何地方**——用户点进看脚本树时，自定义积木的内容是缺的。

要真正"看到脚本树全貌"，得补一个只读积木：

| 改动 | 内容 |
|---|---|
| `Blocks.java` | 注册 `procedures.definition`（HAT 形状，文本「定义 {NAME}」） |
| `Sb3Importer` | 不再跳过，把它作为独立脚本的链头，函数体接在 `next` |
| `ProjectWriter` | 反向写回 `procedures_definition` |

约 60 行。不补的话，带自定义积木的工程查看时会出现「定义了但内容消失」的错觉。

### 2. 单脚本开关 = **整包重启**

关掉一份脚本后必须 `loadProject` 重新加载整个工程，所有线程从头开始。也就是说：

- `forever` 循环里的状态、变量值都会重置；
- 其他正常运行的脚本也会被打断重来。

这是 scratch-vm 的结构决定的（没有"热插拔单脚本"的接口）。三种选择：

| 选择 | 行为 | 代价 |
|---|---|---|
| **A. 立即生效 + 整包重启** | 点一下即重载 | 其他脚本状态重置，需在界面写明 |
| B. 标记延迟生效 | 只改标志，下次启用引擎才生效 | 用户点了没反应，容易误判为坏了 |
| C. 按线程精确停止 | 关掉的只停对应 VM 线程 | 需要脚本 ID ↔ 线程映射，scratch-vm 未暴露，改造量大 |

建议 A，并在开关旁加一行灰字：「切换会重启全部脚本」。

### 3. 改名后重复导入会去重失败

现在的去重键是「名字 + 角色」：

```java
if (sameFileName(existing.name, definition.name) && existing.scopeId.equals(...))
```

改名后名字变了，同一个 sb3 再导入会多出一套副本。改法：给 `ScriptDefinition` 加一个 `sourceId`（sb3 文件名 + 角色 + 序号），去重改用它。约 15 行。

**两者真正的差别是**：`Blocks`（428 行）这份界面定义是否值得为"看一眼"而长期维护。

我倾向**按四条需求做**——您明确要"能进去看"，这个价值高于 428 行的维护成本；而且开关能力在只有 sb3 的整体模式下是做不到的。

但要说清一件事：`Blocks` 与扩展的积木定义是**两份平行数据**，新增积木必须同步，否则新积木在查看界面会显示成红字「未知积木」。这是长期成本，不是一次性的。
