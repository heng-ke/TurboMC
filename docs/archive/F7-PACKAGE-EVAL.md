# F7 第三版评估：按包分组 + 包级开关

## 一、这个改动解放了什么

上一版之所以要留 `ProjectWriter`（568 行），是因为**单脚本开关**需要"过滤脚本后重新序列化"。

改成包级开关后，开关作用在整包上：**启用就是以 sb3 原样加载，禁用就是不加载**。中间那层序列化完全没有存在的必要。

```
旧：sb3 → 解析 → 单脚本开关 → 重新序列化 → 加载
新：sb3 ──────────────────→ 加载        （开关决定加不加载）
```

`ProjectWriter`、`ScriptDefinition.enabled`、`ScriptStore` 的整套脚本级增删改，一起作废。

## 三、必须您定的一件事：多包能否同时启用

这是本版唯一的分叉，两条路的成本差一倍多。

### 方案甲：互斥（一次只有一个包）

- 开关是**单选**，点另一个包会自动关掉前一个；
- `ScriptEngine` 直接 `loadProject(那个 sb3)`，零改造；
- 净减约 **1900 行**，无新增风险。

### 方案乙：并存（多个包同时跑）

需要新增一个**工程合并器**（约 120 行）：把 N 个 sb3 的 `targets` 拼成一个 project.json。

四个技术点：

| 点 | 处理 | 风险 |
|---|---|---|
| **Stage 只能有一个** | 保留第一个包的 Stage，其余包的舞台变量并入 | 高：变量 ID 冲突会让另一包的全局变量读不到 |
| **角色名冲突** | 给每个 target 改名加包前缀（`挖矿/角色1`） | 中：改名会影响该角色内脚本的局部变量作用域标识，需同步改 `scopeId` |
| **extensions** | 并集 | 低 |
| **monitors / 造型** | 忽略（本就不加载资源） | 低，但角色会无贴图 |

**我的判断**：乙才是"包"这个概念的真正价值——一个包管挖矿、一个包管战斗，组合起来用。但舞台变量合并这一项不做扎实，用户会遇到"另一包的全局变量神秘失效"，且**完全静默**（和之前 chat 那个 bug 同类型）。

如果暂时不想承担这个风险，甲也成立：开关变成"切换当前工程"，语义清晰、零 bug 面。后续想升级到乙，随时可以加。

## 四、存储结构变化

```
config/hk-script/
├── packages/
│   ├── 作品.sb3
│   ├── 挖矿.sb3
│   └── index.json        ← 包名、启用状态
└── scripts/              ← 旧编辑器脚本，本版起作废
```

`scripts/*.json` 是编辑器私有格式，`ProjectWriter` 删除后无法再转成 sb3。

**删除前必须做一次导出**：现在列表页的「导出」按钮仍可用（走 `ProjectWriter`），对要保留的脚本导一次 .sb3，确认 TurboWarp 能打开，再删。

## 五、其他连带的必改点

### 1. 按键触发会失效

`ScriptEngine.triggerKeys()` 现在是遍历编辑器脚本读 `KEY` 字段。编辑链一删必然空集。

改法：不再收集键名，改成**逐键触发**——

```
每帧：对 InputKeys 里"刚按下"的键 → startHats("event_whenkeypressed", {KEY_OPTION: key})
```

`KEY_OPTION` 是 field，`startHats` 的字段匹配支持。约 20 行，不需要任何 sb3 解析。

### 2. 解析结果要缓存

列表里每个包都要 `Sb3Importer` 解析一次才能显示脚本名。单包 < 10ms，但每次打开 F7 都全量解析不必要。

加一个 `Map<Path, Result>` 缓存，文件修改时间变了才重解析。约 30 行。

### 3. 自定义积木的函数体仍然看不见

`Sb3Importer` 跳过 `procedures_definition`，函数体不挂载。补一个只读积木 `procedures.definition`（约 60 行）。

这一项与包架构无关，是"查看"需求的完整性要求。

## 七、建议

1. **先做导出**，把要留的编辑器脚本转成 sb3（`ProjectWriter` 删除前唯一窗口）；
2. 先按**方案甲（互斥）**落地——它能立刻带来 1900 行削减且没有静默 bug 风险；
3. 补 `procedures.definition`（60 行）让查看完整；
4. 真机跑一轮；
5. 确认需要组合运行后，再做方案乙的合并器（含舞台变量合并的专项测试）。

理由：甲到乙是可以增量升级的（只新增合并器，不改已有结构）；而乙的舞台变量合并如果做错，是**静默失效**——和刚修完的 chat 那个 bug 一模一样的性质，不值得在没有真机节奏的情况下一次赌两把。
