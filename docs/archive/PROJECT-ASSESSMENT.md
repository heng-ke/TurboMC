# hk-script 技术评估文档

> 面向组内项目评估。**本文只陈述事实与判断，不做宣传。**  
> 数据采集日期：2026-11-04（对应 jar `hk-script-1.0.0.jar`，242 KB）

---

## 0. 一页结论

**一句话**：这是一个"用 Scratch 语法驱动 Minecraft 操作"的客户端自动化模组，**执行内核已完成并经过系统验证，编辑器与发布配套尚未收口**。

| 维度    | 评分    | 依据                                  |
| ----- | ----- | ----------------------------------- |
| 功能完整度 | ★★★★☆ | 104 个积木、6 类触发源、`.sb3` 导入、游戏内树形编辑器    |
| 架构与解耦 | ★★★★★ | 执行内核不依赖任何 Minecraft 类型，可脱离游戏运行与自检   |
| 代码质量  | ★★★★☆ | 分层清晰、命名一致；但存在 1200 行单文件与 500 行以上大类  |
| 可测试性  | ★★★★☆ | 34 项启动自检（每次启动都跑）；**无 JUnit，无 CI**   |
| 文档完备度 | ★★★★★ | 5 份专题文档，含上游源码级对照与逐条缺陷证据             |
| 发布就绪度 | ★★☆☆☆ | `fabric.mod.json` 仍是模板、无 CI、无版本升级策略 |

**评估建议**：

- **可以接手维护**——内核边界干净，改动集中在明确的几层；
- **不建议直接对外发布**——元数据、CI、版本策略三项未做，属于 2–3 天的收尾工作；
- **最大的技术债不是代码，是"没有自动化回归"**——34 项自检是运行时断言，不是 CI 门禁。

## 1. 项目定位与边界

### 1.1 做了什么

用 TurboWarp（Scratch 3 编辑器）编排脚本 → 导出 `.sb3` → 游戏内导入 → 引擎解释执行 → 驱动 Minecraft 客户端操作（挖掘、移动、攻击、开箱、看视角…）。

同时保留一套游戏内树形编辑器，用于快速调试与查看导入的脚本结构。

### 1.2 明确不做什么

| 不做                     | 原因                                       |
| ---------------------- | ---------------------------------------- |
| 运动 / 外观 / 声音 / 画笔 / 克隆 | 2D 舞台语义与 3D 世界无对应，硬映射会产出"看着对、落点全错"的假语义   |
| 操作 Scratch 角色          | 产品定位是"编排自动化逻辑"，不是"移植 Scratch 项目"         |
| 服务端 / 多人同步             | 纯客户端模组，动作通过正常客户端输入通道发出                   |
| 脚本沙箱                   | 脚本只能调用白名单内的原生动作，没有任意代码执行能力（对比外挂 Node 方案） |

### 1.3 用户画像

愿意用图形化编程组织重复劳动的 Minecraft 玩家；不需要写 Java，但需要理解"触发—条件—动作"。

## 3. 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│ 载体层（依赖 Minecraft）                                      │
│  HkScriptClient: F6 启停 / F7 编辑器 / tick 驱动              │
│  config: HkScriptConfig + Cloth 界面                          │
└───────────────┬─────────────────────────────────────────────┘
                │
┌───────────────▼─────────────────────────────────────────────┐
│ 引擎门面   ScriptEngine                                      │
│  装载脚本 / 触发分发 / 停机策略 / 每 tick 驱动调度器            │
└───────┬───────────────────────────────┬─────────────────────┘
        │                               │
┌───────▼──────────┐          ┌─────────▼──────────────────┐
│ 解析层            │          │ 执行层                      │
│ sb3/Sb3Parser     │          │ ir/Compiler → ir/Op 指令流   │
│ sb3/Sb3Mapping    │          │ runtime/ScriptInstance 解释  │
│ node/BlockNode    │          │ runtime/ScriptScheduler 调度 │
│ store/ScriptStore │          │ runtime/Values/Scratch* 语义 │
└───────┬──────────┘          └─────────┬──────────────────┘
        │                               │
┌───────▼───────────────────────────────▼─────────────────────┐
│ 动作层（唯一与游戏世界交互的地方）                              │
│  action/GameActions（挖掘/移动/攻击/开箱…）                    │
│  action/MathFunctions、SensingActions、ListFunctions         │
│  action/NativeRegistry（id → 实现，积木只引用 id）             │
└─────────────────────────────────────────────────────────────┘
```

**核心设计**：执行内核（`ir` + `runtime`）**不 import 任何 `net.minecraft.*`**，通过 `ScriptContext.handle`（`Object`）与 `NativeRegistry` 间接访问宿主。这是能脱离游戏做自检、也是本次重构能在 5 小时内完成四批改动的前提。

### 数据流

```
.sb3 ──unzip──▶ project.json ──Sb3Parser──▶ BlockNode 树
                                              │
                              ┌───────────────┴───────────────┐
                              ▼                               ▼
                       游戏内编辑器展示                  Compiler 编译
                       （TreeView + 参数面板）                │
                                                              ▼
                                                     扁平指令流 List<Instr>
                                                              │
                                          ScriptScheduler.tick（双层预算）
                                                              │
                                    ScriptInstance.step（栈式解释，遇 YIELD 让出）
                                                              │
                                              NativeRegistry 查表 → GameActions
                                                              │
                                                        Minecraft 客户端
```

## 4. 核心机制

### 4.1 积木模型（`BlockNode`）

- 树形结构：`fields`（下拉/常量）、`inputs`（表达式槽）、`branches`（C 形槽）、`next`（同级链）。
- 104 个注册积木，按分类：`world` 29、`action` 17、`operator` 19、`control` 12、`list` 10、`event` 6、`sensing` 4、`debug` 3、`data` 2、`func` 1。
- 参数分两类，**读法不同**，是新增积木时最容易出错的地方：`fieldText/fieldOption` 读 `fields`，`text/number/bool` 压 `inputs`。

### 4.2 编译与 IR

- 栈式虚拟机，指令集 21 个 opcode（`PUSH_CONST` / `LOAD_VAR` / `BIN_OP` / `COMPARE` / `JUMP` / `YIELD` / `LOOP` / `SPAWN` / `CALL_FUNC` / `CALL_ACTION` / `CALL_BUILTIN` / `BROADCAST_WAIT` / `STOP_ALL` / `HALT` …）。
- 编译期解析跳转目标，`SPAWN`/`CALL_FUNC` 先占位后回填。
- **指令数上限保护**：单链 10000 条，防环。

### 4.3 调度器

| 机制   | 实现                             | 目的                                      |
| ---- | ------------------------------ | --------------------------------------- |
| 双层预算 | 每实例 ≤400 条/tick，全局 4000 条/tick | 防单脚本卡帧、防多脚本叠加掉帧                         |
| 公平分配 | 按"剩余实例数"均分 + 每实例保底 32 条        | 避免排在后面的实例永久饥饿                           |
| 触发策略 | 广播/常驻=重启，按键=已在跑则放弃，伤害/聊天=并发    | 对齐 Scratch `startHats` 语义               |
| 实例上限 | 每脚本 4 个，全局 64 个                | 防触发风暴                                   |
| 循环节流 | 可选（`LOOP.b`），默认关闭              | 关闭=一个 tick 内尽量多跑；开启=每轮一 tick（同 Scratch） |
| 并发安全 | 遍历期间新建入 `pendingAdd`，tick 结束并入 | 广播与 `spawn` 都会在遍历中新建实例                  |

### 4.4 变量作用域（三层）

| 层       | 存储                                | 对应 Scratch | 内部名示例            |
| ------- | --------------------------------- | ---------- | ---------------- |
| 实例局部（0） | `ScriptInstance.locals`           | 函数参数、临时变量  | `$p1`、`$repeat0` |
| 全局（1）   | `GlobalVariables`                 | Stage 变量   | `score`          |
| 角色（2）   | `TargetVariables`（按 `scopeId` 分表） | "仅适用于当前角色" | `Sprite1/score`  |

导入时按**变量 ID** 定位（Scratch 字段是 `[名字, ID]`），内部名加角色前缀，**ID 相同才视为同一变量**。显示层省略当前角色前缀。

### 4.5 sb3 导入

处理的关键格式点：

- `inputs` 的 1/2/3 类型码；类型 3 的"遮蔽 shadow"回退
- 内联原语 `[12 变量]` / `[13 列表]` / `[11 广播]` / `[4-8 数字]`
- `mutation`：`procedures_*`（字符串化 JSON 数组）、`control_stop` 的 `hasnext`
- 未映射积木 → `control.nop` 占位并**继续链接**（否则会吞掉后续整段代码）
- 三元展开：`data_changevariableby` → 读/加/写；`control_wait`、`looks_sayforsecs` → 秒×20 转 tick
- 导入报告：`ParseResult.summary()` 输出"导入 N 个脚本，跳过 M 块（opcode 列表）"

### 4.6 TurboWarp 扩展

`turbowarp/hkscript-extension.js`（13 KB）提供 50 个扩展积木（18 动作 + 29 世界查询 + 3 调试），中英双语 + 菜单本地化。用户在 TurboWarp 里加载该 JS 后即可拼装游戏动作。

## 6. 质量保障

### 6.1 启动自检（34 项）

每次启动在渲染线程跑一遍纯逻辑断言，任一失败则**停用引擎**并打日志：

```
[script] 自检通过：34 项检查全部正常
[script] 引擎就绪：注册积木 104 个
```

覆盖范围：跳转目标合法性、原生引用完整性、循环计数、`repeat until` / `wait until`、列表索引、`spawn`、自定义积木、sb3 切片（含秒→tick 换算）、菜单参数落位、`if-else` 双分支、等待挂起、预算、停止全部、变量作用域、语义层（18 条）、调度与线程策略、循环节流、感知与输出、自定义积木导入、广播并等待。

**优点**：不依赖 MC，启动即验证；断言与缺陷一一对应（多数断言写在对应修复的同一批次）。  
**短板**：只在运行时跑，不能作为 CI 门禁；`SelfCheck.java` 已 1221 行。

### 6.2 构建与验证流程

```
./gradlew compileClientJava    # 秒级，改一处就编译
./gradlew build                # 出 jar
./gradlew runClient            # 启动，看自检与导入日志
```

实际开发中每批改动都跑一遍完整构建 + 启动验证。**没有自动化 CI。**

### 6.3 已知的验证盲区

- 编辑器 UI 无自动化测试，靠人工点。
- 游戏动作（挖掘/移动）无法脱离游戏验证，只能靠实机。
- 无长时间稳定性测试（例如连续跑 30 分钟脚本的内存/句柄曲线）。

## 8. 关键设计决策

| 决策                         | 理由                                  | 代价                            |
| -------------------------- | ----------------------------------- | ----------------------------- |
| **自己写解释器，而不是嵌 scratch-vm** | 单 jar 分发；避免数十 MB 的 JS 引擎依赖与宿主适配层    | 语义需逐条对齐上游（本次已对齐 22 项缺陷）       |
| **执行内核与 MC 解耦**            | 能脱离游戏做自检；重构风险可控                     | 动作层需要一层 `NativeRegistry` 间接调用 |
| **变量名加角色前缀而非改 IR**         | IR 的变量字段不动，作用域靠命名空间                 | 内部名对用户不可读，需显示层剪裁              |
| **循环节流默认关闭**               | 产品定位是自动化效率，不是动画节奏                   | 与 Scratch "每帧一轮"存在偏差，需手动开启    |
| **未映射积木用占位符而非跳过**          | 跳过会截断后续积木链（曾导致"脚本只跑一半"）             | 编辑器里会出现"（不支持的积木）"占位块          |
| **广播=重启而非叠加**              | 对齐 Scratch `startHats`；避免高频广播跑出多份并发 | 依赖"叠加"的旧脚本行为会变                |

## 9. 风险登记

| #   | 风险                                                      | 严重度 | 影响                   | 缓解                              |
| --- | ------------------------------------------------------- | --- | -------------------- | ------------------------------- |
| R1  | `fabric.mod.json` 仍是模板（description / authors / license） | 高   | 无法对外发布               | 发布前必改，半小时                       |
| R2  | 无 CI，回归只靠启动自检                                           | 高   | 改坏语义可能到实机才发现         | 把 SelfCheck 抽成可独立运行的 main，接入 CI |
| R3  | 版本锁死 1.21.11                                            | 中   | MC 升级需改 mixin / API  | 无。需要时单独排期                       |
| R4  | `SelfCheck.java` 1,221 行且持续增长                           | 中   | 阅读与维护成本上升            | 按主题拆分（sb3 / 语义 / 调度）            |
| R5  | 编辑器无撤销/重做                                               | 中   | 误删需手工重拼              | 待排期                             |
| R6  | 无反向导出（脚本 → sb3）                                         | 中   | 游戏内改的脚本回不到 TurboWarp | 约 1 天工作量                        |
| R7  | 循环节流默认关闭                                                | 低   | 与 Scratch 时序不一致      | 配置项可开，已在界面标注                    |
| R8  | 除零返回 0（Scratch 返回 Infinity）                             | 低   | 极端表达式判断不同            | 有意偏差，可配置化                       |
| R9  | 性能预算为硬编码常量                                              | 低   | 低配机器可能掉帧             | 可改为自适应（按帧耗时反馈）                  |
| R10 | 动作层依赖实机验证                                               | 中   | 无法在 CI 覆盖            | 只能靠测试清单 + 人工回归                  |

## 12. 给评估组的三问

**1. 能不能用？**  
能。83 个积木覆盖"采集—战斗—移动—开箱"常见自动化，`.sb3` 导入实测可用，启动自检全绿。

**2. 敢不敢维护？**  
敢。执行内核与游戏解耦，改动边界清晰；本次四批重构（5 小时）在 22 项自检保护下完成，未引入回归。**前提是先补 CI**——否则下一个接手的人只能靠"启动看日志"。

**3. 值不值得继续投？**  
取决于目标：

- 若目标是**内部自动化工具**，当前状态已可用，投入 2 天收尾即可交付；
- 若目标是**对外发布的模组产品**，还需补：发布配套（0.5 天）、CI（1 天）、实机回归（2 天）、文档面向用户重写（1 天）。
