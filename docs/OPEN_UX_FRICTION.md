# 用户可感知的摩擦（未决）

> 用途：从**使用者视角**已核实、但**尚未决策**的摩擦点、现状证据与候选方案。
> 已落地的五项（UX-01 / 05 / 06 / 07 / 08）不再在此记录：结论在 `BACKLOG.md` 的状态列与
> `ARCHITECTURE.md`（§三 的圆点与置灰语义、气泡停留与画框上限两处配置）。
> 本文只记录「哪里还不友好、可以怎么改」，不含决定（见 `docs/README.md` 维护约定第 4 条）。
> 最后核对：2026-11-23。

## 一、范围与视角

| 角色 | 典型动作 | 最怕什么 |
|---|---|---|
| 新装模组的玩家 | 装 jar → 进世界 → 想跑别人做的脚本 | 装完什么都没变，不知道下一步按什么 |
| 脚本作者 | TurboWarp 写积木 → 导出 sb3 → 反复调 | 脚本失败时拿不到原因，只能靠猜 |
| 服主 / 长期使用者 | 每局启用、多个工程切换 | 状态不透明、切换有隐性副作用 |

这个项目的失败路径并非「静默」：8 态状态机各态有独立文案、导入失败带文件名与原因、
扩展 opcode 与 jar 版本自检常驻 HUD、单帧执行预算超时只跳帧不停线程。因此下面只列
**仍然缺的东西**，不再重复这些已成立的部分。

## 二、仍未决的摩擦

严重度按「是否阻断首次跑通」划分，不按修复成本。

### P0 —— 阻断从零到第一次跑起来

#### UX-02 新手没有可跑的起点

- **用户感受**：「面板让我把 .sb3 放进 imports，可我手上一个 sb3 都没有。」
- **现状**：空列表提示完整（`lang/zh_cn.json` 的 `no_packs`），但仓库里没有任何示例工程；
  `imports/` 下的 `DS.sb3`、`作品.sb3` 等是本地测试文件，不入库。
- **候选**：
  1. 随 jar 附带 `example.sb3`（走到坐标 → 说一句话 → 画一个框），首次启动释放到 `imports/`，
     与扩展 js 同一套 `ExtensionExporter` 机制。
  2. 只在空列表加「载入示例」按钮，点击时从 jar 内解出。
  3. 文档里提供下载链接。**不推荐**：离线玩家拿不到。
- **取舍**：方案 1 会让第一次进游戏的 imports 里凭空多一个包，需要在首次导入逻辑里避免
  自动启用它（`ScriptListScreen` 的 `doImport` 会自动接手第一个包）。

### P1 —— 脚本作者的日常踩坑

#### UX-03 阻塞动作失败后，脚本与玩家都无从得知

- **用户感受**：「机器人卡在墙前 60 秒，然后继续执行挖矿，像什么都没发生。」
- **现状**：寻路放弃时只写日志（`PathFollower.finish`），`moveToward` 在扩展里是 `command`，
  没有对应的 reporter；脚本无法分支，HUD 也没有失败态。
- **关联**：**这不是新问题**。`BACKLOG.md` 的 PATH-02（失败后脚本线程的归宿）、PATH-03
  （失败是否对玩家可见）已记录在 `OPEN_MOVE_PREEMPTION.md` §五；本文只补充使用者侧佐证，
  不重新论证方案。
- **候选**：见 `OPEN_MOVE_PREEMPTION.md` §五、§六；从体验看，最少需要「失败对玩家可见」这一半。

#### UX-04 容器点击的异步语义没有内建等待

- **用户感受**：「点了槽位立刻读，永远读到旧数据，以为积木坏了。」
- **现状**：`ContainerActions` 的注释明确「同一 tick 内读到的仍是旧值，脚本应至少等 1 tick」，
  但这是文档级约定，积木本身不等待、不返回成功与否。
- **候选**：
  1. 点击积木内建等待一 tick 后返回（对作者免费，代价是积木多阻塞 1 tick）。
  2. 新增「等待容器响应」积木（显式，但需要作者知道要用）。
  3. 维持现状，只在积木 tooltip 写明。
- **取舍**：方案 1 与「点击是异步」的物理事实最贴合，但会让连续点击的脚本节奏变化，
  属行为变更，需同步 `CONTAINER.md` 与冒烟断言。

### P2 —— 细节

#### UX-09 只读查看器没说「去哪改」

- **现状**：底部提示为「Esc 返回（只读）」，只说不能改，不说去哪改；列表页的 `pack_hint`
  已有「脚本请在 TurboWarp 中编辑」，查看器里没有。
- **候选**：改成「Esc 返回 · 只读，修改请回 TurboWarp」。一行文案，零风险。

#### UX-10 脚本崩溃的完整原因只在日志里

- **现状**：`RuntimePanelScreen.buildLines()` 只渲染 `statusDetail`（一行、可能被截断），
  完整堆栈只在 `logs/latest.log`；面板无复制入口。
- **候选**：
  1. 面板内滚动区展示完整错误文本。
  2. 加「复制错误」按钮（`client.keyboard.setClipboard`）。
- **取舍**：错误文本可能很长，需要滚动区；面板已是列表结构，改造成本中等。

#### UX-11 只有中英两种语言，文档全中文

- **现状**：`lang/` 下仅 `zh_cn`、`en_us`；README 与 `docs/*` 均为中文。界面能被英文玩家
  看懂，但使用路径读不了。
- **候选**：README 提供英文版（或顶部一句「English summary」链到 wiki）。
- **取舍**：文档翻译的维护成本高于收益，除非有明确的非中文用户群。

## 三、建议顺序

1. UX-02：示例工程，需要设计「首次导入不自动启用」的规则，单独立项。
2. UX-09：一行文案，可随时顺手做。
3. UX-03：与 PATH-02/03 合并决策，不单独推进。
4. UX-04：属行为变更，需连同 `CONTAINER.md` 与冒烟断言一起改。
5. UX-10：按实际反馈决定。
6. UX-11：明确不做，除非出现非中文用户需求。

## 四、明确不做

- **游戏内积木编辑器**：架构已定（脚本在 TurboWarp 写，游戏内只读），不要因为
  「查看器不能改」而推翻。
- **UX-11 的多语言文档**：除非出现明确的非中文用户反馈，否则不做机器翻译级补全。
