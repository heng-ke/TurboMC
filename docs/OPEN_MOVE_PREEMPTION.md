# 「走向」会话被抢占：现状与待决策

> 状态：**事实已核对，未做代码改动；D1–D4 仍未决。**
> 记录 2026-11-08；2026-11-23 瘦身——删去已并入 `ARCHITECTURE.md` 的旁支结论、随实现漂移的行号清单，
> 以及与 §二 重复的独立章节。缺陷仍在：`PathFollower` 的 `session` / `lastState` 是静态单例，
> `finished()` 仍是「非 IDLE 且非 FOLLOWING」，四种终态折叠成一个布尔值。

## 一、缺陷

原始描述（Issue #2 及后续追问）：

1. 脚本 B 开始「走向」会把脚本 A 的移动会话置成 `CANCELLED`；
2. `poll("move")` 把 `CANCELLED` 也当成「已完成」，于是 A 提前放行；
3. A 以为自己到了，后续的点击 / 挖掘全部错位。

衍生追问的答案是：并发单位是 VM 线程而不是玩家，所以单个玩家也能有两条走向（§三）；
A 不会在抢占那一刻立刻放行，而是在**抢占者的终态**之后放行（§二）。

## 二、核对结论

| 论断 | 结论 | 依据 |
|---|---|---|
| B 起「走向」会把 A 的会话置成 CANCELLED | **成立**（同目标除外） | `PathFollower.start()`：同目标复用，否则 `closeSession()` |
| A 因这次 CANCELLED 立即放行 | **不成立**：该 `lastState` 的存活窗口为 0 帧 | `closeSession` 写 CANCELLED，同调用内 `start` 覆盖为 FOLLOWING |
| `poll("move")` 把 CANCELLED 当已完成 | **成立** | `finished()` 只排除 IDLE / FOLLOWING |
| A 会被提前放行 | **成立**，放行者是「B 的终态」，不是「B 的 start」 | 同上 |
| 放行后点击 / 挖掘错位 | **成立**，且无任何位置校验 | `vm-bootstrap.js` 的等待只认 poll 布尔值 |
| 玩家只有一个 → 不会有两条走向 | **不成立**：并发单位是 VM 线程 | `vm.es5.js` `stepThreads()` 遍历 `runtime.threads`，`PROMISE_WAIT` 只跳过该条 |

关键点：`closeSession` 设的 `CANCELLED` 与 `start` 覆盖回 `FOLLOWING` 之间没有让出线程的调用，
而 A 的观测点在帧首、B 的执行点在帧中，**A 永远看不到那次 CANCELLED**。

## 三、为什么单玩家也有两条走向

`stepThreads()` 逐条推进 `runtime.threads`，处于 `PROMISE_WAIT` 的线程只被跳过，不影响其他线程。
因此「A 在等位移」不等于「引擎停了」。能同时存在的两条移动线程：

1. 绿旗主循环 +「当聊天包含」帽子里的走向；
2. 主循环里的走向 +「当受伤 / 当死亡」帽子里的逃生走向；
3. 同一角色的多个「当绿旗被点击」帽子（`startHats` 不查重）；
4. 多个角色各带脚本（`Sb3Importer` 遍历全部 targets）；
5. 「当按下键」帽子（edge-activated，每次触发压一条新线程）。

**不会**发生的只有一种：单条线程内顺序写「走向 A → 走向 B」——走向阻塞，第二块在第一块放行后才执行。
另注：引擎同时只运行一个工程（包级互斥），所以「脚本 A / B」只可能是同一工程内的两条线程。

## 四、失败是静默的：三种放行情形

| 触发放行者 | 时机 |
|---|---|
| B 到达 / 放弃 / 超时 | B 终态后的下一帧 |
| 引擎中止（离开世界、停止全部、切工程、断开） | 下一帧 |
| A 自己的等待上限到期（1240 tick ≈ 62 s） | 到点无条件放行 |

第三条常被忽略：**即使没有任何抢占，走向失败后的放行也是静默的**，因为 `poll` 只有布尔值。
这也是 D2 与 D3 必须一起定的原因。

## 五、待决策项（未定）

### D1. 脚本之间的走向冲突，采用哪种语义

| 选项 | 行为 | 主要代价 |
|---|---|---|
| 无条件抢占（现状） | 后来者杀掉前者 | 无 postcondition；活锁；优先级缺失 |
| 拒绝后来者 | B 的走向失败，A 继续 | 「玩家改变主意」必须显式停止 |
| 排队 | B 等 A 结束 | 队头不结束会永久等待 |
| 分层优先级 | 玩家 / 引擎指令可抢，脚本之间不可 | 需要定义归属与优先级 |

分析意见（非决定）：无条件抢占的优点（响应快、无死等）只在「玩家亲自下指令」时成立；
在两条脚本线程之间，它的优点用不上、缺点全部生效。

### D2. 走向失败后，脚本线程的归宿

| 选项 | 效果 | 备注 |
|---|---|---|
| 继续执行（现状等价） | 立即跑下一块 | 即时错位，故障密度最高 |
| **中止这个脚本** | 线程结束 | 等价 `control_stop "this script"`，技术可行 |
| 原地重试 | 重新 start 同目标 | 与抢占者互抢 → 活锁 |
| 停在原地 | 线程永不继续 | 脚本「失踪」 |

与 D1 强耦合：只做「通知」不做「归宿」，会把低频延迟错位换成高频即时错位。

### D3. 失败是否对玩家可见

仅日志（现状） / HUD 红字 / 新增 reporter 积木「上次走向结果」（arrived / gave_up / timeout / cancelled）。

### D4. 是否引入显式「停止走向」积木

若 D1 选「拒绝」，这类积木是打断的唯一合法手段；若选「无条件抢占」，它的语义会退化为
「停止当前」，价值有限。

## 七、复现与验证

**最小工程**：一个角色、两个帽子——`当绿旗被点击 → 重复执行 { 走向(100,64,100)；挖掘 }`，
`当聊天包含「回来」→ 走向(0,64,0)`。绿旗启动等 2 秒（线程 1 处于 `PROMISE_WAIT`），再发「回来」。

**期望日志**：`[path] 中止：…`（A 被 `closeSession`，reason 当前为「未知」）→ `[path] 到达：…`（B 的目标）
→ 随后出现线程 1 的「挖掘」，位置在 B 的终点而非 (100,64,100)。

**建议回归用例** `vmTwoMove`（照 `build.gradle` 中 `vmChat` / `vmKeyHat` 的样式注册），断言：
A 的等待不被 B 的终态放行；A 的 ticket 能拿到 `CANCELLED`；B 正常到达。
当前实现下该用例必然失败，可作为缺陷基线。

## 八、旁支结论

1. **`__tmcPending` 是 VM 级共享数组**（`vm-bootstrap.js`）：所有线程的等待项并列，同一个
   `check="move"` 会被同一终态同时放行——影响面是「所有正在等 move 的线程」，不是单个。
2. **`TurnSession` 是同一结构**：`session` / `lastState` 同为静态单例，`start()` 直接覆盖会话，
   `finished()` 只认 DONE / ABORTED。修 `PathFollower` 时需一并评估（路径见
   `action/motion/TurnSession.java`）。
